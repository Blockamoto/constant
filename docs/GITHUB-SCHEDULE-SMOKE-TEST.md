# Scheduled GitHub capability smoke test

## Purpose

The first scheduled Constant run must establish what a **scheduled ChatGPT task** can and cannot do through the connected GitHub integration.

Do not infer scheduled capability from an interactive chat. Test it.

The run should be safe, reversible where possible, and leave a durable result.

## Target

Repository: `Blockamoto/constant`

Default branch: `main`

## Run identity

Generate a UTC run key:

`YYYYMMDDTHHMMSSZ`

Use it consistently in branch names, issue text, file names and the final report.

## Tests

Record each capability as one of:

- `PASS`
- `DENIED`
- `UNAVAILABLE`
- `ERROR`
- `NOT_TESTED`

Never silently skip a failed operation.

### A. Read

1. Locate `Blockamoto/constant`.
2. Read `README.md`.
3. Read the latest commit metadata.
4. Search or enumerate branches if the connector supports it.
5. Read open issues and pull requests if supported.

### B. Issue lifecycle

1. Create an issue titled `Smoke test <run-key>`.
2. Add a comment containing the run key.
3. Edit the issue body.
4. Close the issue.

Do not delete it. The closed issue is useful audit evidence.

### C. Branch write

1. Create branch `smoke/<run-key>` from current `main`.
2. Create `smoke-tests/runs/<run-key>.md` on that branch.
3. Read the file back and verify the exact run key appears.

The file should say only that it was generated by the scheduled smoke test. Do not put secrets or connector metadata in it.

### D. Pull request lifecycle

1. Open a PR from `smoke/<run-key>` to `main`.
2. Add a PR conversation comment.
3. Read the PR back.
4. Merge the PR if permitted.
5. Verify the merged file is readable on `main`.

If merge is denied, leave the PR open and mark the capability accordingly. Do not repeatedly retry a permission denial.

### E. Direct-to-main write

After the PR test, attempt a separate direct write:

`smoke-tests/direct-main/<run-key>.md`

Then read it back from `main`.

This test matters because interactive ChatGPT writes and scheduled ChatGPT writes may have different permission behaviour.

### F. CI visibility

The repository includes a validation workflow.

For a commit produced by the smoke test:

1. query workflow/check status if available
2. read run/job metadata if available
3. if logs are available, read a small relevant portion

Do not deliberately break the workflow merely to test re-run controls.

### G. Capability inventory

At the end, inspect the GitHub actions actually exposed to the scheduled environment and note useful capabilities that were not exercised because they would be destructive, irrelevant or require an existing failed run.

Examples:

- file update/delete
- labels
- review actions
- workflow re-run
- branch deletion
- releases

The report should distinguish **tool exists** from **permission verified**.

## Result record

Write the final report to:

`smoke-tests/reports/<run-key>.md`

Use this shape:

```md
# GitHub scheduled capability smoke test

Run: <run-key>

| Capability | Result | Evidence / note |
| --- | --- | --- |
| Repository read | PASS | ... |
| File read | PASS | ... |
| Issue create | PASS | ... |
| Issue comment | PASS | ... |
| Issue edit | PASS | ... |
| Issue close | PASS | ... |
| Branch create | PASS | ... |
| Branch file write | PASS | ... |
| PR create | PASS | ... |
| PR comment | PASS | ... |
| PR merge | PASS | ... |
| Direct main write | PASS | ... |
| CI status read | PASS | ... |

## Conclusion

<Plain-English description of the reliable operating envelope.>
```

If direct main writing is not available, put the report on the smoke branch and ensure the PR remains accessible.

## Cleanup

Do not erase the evidence of the first run.

For later repeated probes, stale smoke branches may be deleted after merged results are safely recorded, but the reports, merged test files and closed issues should remain as a capability history.

## Success criterion

The output of this exercise is not "everything passed."

The output is a trustworthy map of the scheduled environment. A cleanly documented limitation is a successful finding.
